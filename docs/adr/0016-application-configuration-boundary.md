# ADR 0016: Persistent Application Configuration Boundary

- Status: Accepted
- Date: 2026-09-05

## Context

The existing long-running BBC process is driven by configuration generated by
the local scenario runner. That document contains an ephemeral actor identity,
dynamic ports, and a test-control token. It is intentionally loopback-only and
is unsuitable as a persistent user configuration.

A normal installation needs a durable description of its wallet, data
directory, network, optional full-node and miner roles, P2P listener, initial
peers, and local command endpoint. It must remain possible to run the existing
multi-process scenarios against the same node, consensus, storage, mining, and
network implementation.

## Decision

- Define a separate strict Application Config version 1 in
  `docs/application-config.md`.
- Require the `wallet` role and allow optional `full_node` and `miner` roles.
- Keep wallet passwords, private keys, and RPC token values outside the
  application JSON.
- Resolve relative paths from the configuration file's directory.
- Reject unknown fields, duplicate roles and peers, invalid cross-role sections,
  unsafe RPC binding, and malformed endpoints before starting a process.
- Keep scenario actor configuration and test control separate. The scenario
  runner invokes `bbc node run --scenario-config`; normal runtime configuration
  will use `--config` after the shared runtime boundary is extracted.
- Provide `bbc config validate` and `bbc config show` before runtime integration
  so configuration behavior has a tested public interface.
- Use a loopback-only authenticated local RPC for commands sent from another
  terminal. The transaction client will sign locally and submit only public
  transaction bytes.

## Consequences

- Existing scenario behavior and wire protocols do not change.
- Users can prepare and inspect stable configuration without depending on
  generated test artifacts.
- The parser may accept a future LAN or public P2P listen address, but parsing
  alone does not expose a service.
- Normal `node run --config`, RPC transport, token creation, configuration
  creation, and local wallet signing remain explicit follow-up integrations.
- Application and scenario schemas can evolve independently without making
  test-only authentication part of the product interface.
